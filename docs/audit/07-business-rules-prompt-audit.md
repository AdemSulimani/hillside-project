# Phase 7 — Business Rules & Prompt Strategy Audit

> **Audit phase 7 of the Hillside AI pipeline audit — the tri-diff.** Compares three artifacts that are supposed to say the same thing: (1) the operator rulebook `business.md` (repo root, **17 rules** — the phase brief said 19; the file contains 17 non-empty rule paragraphs, and the live `ai_configs.restrictions` array is likewise 17 elements, confirming the count), (2) the live prompt surface (13 `prompt_blocks` + runtime appends + restrictions footer — dumped verbatim as **EV-026–EV-029**), and (3) the code enforcement layer (pre-reply paths S-23–S-29, post-reply guards S-45–S-61, draft-order gates S-69–S-73). Verified against source at `backend/src` (working tree, commit `a8ceb15`).
>
> **Headline results:** the 17-rule spec reaches the model for **1 of 6 tenants** (EV-029 — five tenants have an empty restrictions footer; `platform_restrictions` is `[]` everywhere, so the "PLATFORM POLICY" footer has never rendered); **4 rules are prompt-only** with no enforcement mechanism; **5 rules are actively contradicted** by live prompt text or by the guard pipeline (R6, R7, R13, R16, R17), including both rules that say "do not trigger specialist alerts" — dev data shows product alerts firing on exactly the question families those rules protect (EV-010, EV-011), though via adjacent question phrasings and guards the rules' literal scope never bound (see the R16/R17 rows); **7 conflicts/duplications live inside the prompt text itself** (C-01–C-07 below), led by the orphan `offers_promotions` block that references a section no code generates.

Evidence keys: `S-NN` = step ledger (`02-execution-trace.md`), `DP-nn` = divergence register (`03-divergence-analysis.md`, `register/merged.json`), `EV-nnn` = appendix A evidence log. Rules cited as R1–R17 in `business.md` order.

## Prompt architecture assessment

### Assembly order and instruction hierarchy

The system prompt is assembled in a fixed order (`aiService.ts:2249-2298`, then runtime appends at 3919-4092; full map in the prompt mapper):

```
identity/tone/persona → business profile → Product catalog → FAQ →
Guidelines: (tenant_prompt_blocks, sort_order asc) →
~13 runtime appends (2 always-on) →
restrictions footer (OPERATOR BUSINESS RULES + PLATFORM POLICY) — always last
```

Three components claim supremacy simultaneously:

1. `guidelines.messaging_style` — "Brevity (**HIGHEST PRIORITY**)" (EV-026);
2. `SHORTEST_ANSWER_APPEND` — "(**HIGHEST PRIORITY** — this overrides any tone or sales-strategy nudge…)" (`productDescriptionPromptService.ts:196`);
3. the restrictions footer — code comment: "appended last so they are the highest-priority instructions" (`aiService.ts:4086-4088`).

There is no defined resolution when guidelines conflict with the footer or an append: position-last is the only tiebreak, and it protects a footer that is empty for 5 of 6 tenants. The platform's own migration history documents the consequences — 064's header describes an in-prompt contradiction between `recommendations` and the concise-description append "fixed one at a time," and 065 removes "documented in-prompt contradictions #1–#3" between locked guidelines and operator rules.

### Size accounting (unbudgeted)

Per the measured breakdown (prompt mapper §f): a typical text turn is **26,000–33,000 chars ≈ 6,500–8,300 tokens** of system prompt; a 25-product category turn with the restriction-heavy tenant reaches ~40K chars (≈10-11K tokens). The guidelines section alone is **17,907 chars (~4.5K tokens), identical on every turn for every tenant** (EV-027: `variants = 1` on all 13 keys). The only token budget in the pipeline covers conversation history (6,000 est. tokens, `aiService.ts:4019-4023`); the system prompt's own estimate is computed and never read (`aiService.ts:4003`), the estimator is chars/4 with no tokenizer, and no prompt caching is used. Roughly 1.4K tokens of that fixed cost is the same brevity instruction stated three times (C-02/C-06).

### Prompt churn as complexity evidence

**19 of the 68 migrations** (036, 041–043, 049, 050, 052–056, 058, 061, 062-compact, 063–067) create or rewrite prompt-block *content* — 28% of all schema history spent tuning instruction text. The pattern is consistently reactive: 041 narrows verbatim-usage after over-quoting; 052 exists because 042/043's exact-string syncs "silently missed" tenants; 054 narrows an escalation phrase; 064/065 remove documented intra-prompt contradictions; 066 raises the alternatives cap in two blocks (missing the third — C-03); 067 removes a follow-up exception 036 introduced. Each behavioral bug became a migration editing English/Albanian prose — with no test harness for prompt regressions (CI runs no `npm test`).

### The orphan `offers_promotions` block

Live DB has 13 catalog blocks; migrations create 12. `guidelines.offers_promotions` (1,478 chars, EV-026) was admin-created 2026-06-22, catalog-deactivated 2026-06-23 — but **remains `enabled = true` for all 6 tenants** (EV-027) because `assembleGuidelinesFromBlocks` filters on tenant-row `enabled` only (`promptAssemblyService.ts:89`) and no code path disables tenant rows on catalog deactivation (`adminAiController.ts:422-464`; migration 056 shows the manual pattern used for the other retired block). Every prompt therefore instructs the model that "The \"Active offers and promotions\" section above is the ONLY source of truth about offers" — a section **no code generates** (grep over `backend/src`: zero matches). Its final instruction, "If the section shows no offers, tell the customer there are no active offers right now," is precisely what the AI said in EV-012 10946774 ("Nuk kemi oferta aktive për momentin.") — after which the uncertain-answer guard escalated the reply. A dead block instructed the behavior; a live guard punished it.

## Rules that mandate behavior the pipeline undermines

These are the cases where following the operator's written rule *causes* the alert the rule forbids — the strongest tri-diff findings, each anchored in dev data.

### 1. R16/R17: "Do not trigger specialist alerts" — the alerts fire anyway

Both rules end with an explicit no-alert mandate (Albanian live text: "Mos shkakto alarme ose njoftime specialiste për këto pyetje — AI-ja ka të gjithë të dhënat e katalogut të nevojshme", EV-029). The code honors it in exactly one place — the recommendation/comparison exclusion before the gap assessor (`processAIReply.ts:2269-2281`, whose comment restates the rule: "the AI has all the catalog data needed to compare products and answer directly… a false positive, not a genuine knowledge gap"). But:

- **Price questions still escalate through the gap assessor — but the two EV-010 alerts sit on opposite sides of the fix.** The exclusion shipped in commit `86dd1b8` (2026-06-24). EV-010 45247737 (2026-06-23, "sa kushton qikjo optium nutrition gold standart edhe qfar shije e ka" → `missing_info: ["çmimi","shija"]`) **predates it** — at that time no skip existed at all. EV-010 dcf5c812 (2026-06-27, "Me qfar shije i keni edhe sa kushtojn" → alert, answered_info about the *wrong* product) fired **with the exclusion live** and is the instance that proves the residual gap: both messages were tested against the current `RECOMMENDATION_COMPARISON_PATTERNS` set and match nothing — they are single-product price+attribute questions with no comparison phrasing, so the skip cannot fire. The attribute half makes them product-info questions (`attributeIntent.is_product_knowledge_question` / `requestedStructuredAttributes`), and the fail-closed assessor (DP-gg-14) declares the *price* missing — the one attribute R16's rationale says the AI always has. Strictly, neither message is in R16's literal scope (cheapest/most-expensive/comparison); genuinely comparison-phrased questions do hit the exclusion. The contradiction is with the rule's rationale clause, and it survives the 06-24 fix.
- **Recommendation turns still escalate through the name guard.** Conv fcd0af7e (EV-011): the AI answered a "what else do you have?" follow-up by recommending Mega Mass 3kg Qokolad and Mass gainer 3kg Qokolad — both active, in-stock, embedded catalog rows (EV-013) that the AI itself had named two turns earlier. The keyword-less follow-up re-ran retrieval and surfaced 10 *different* catalog products (EV-011 `catalogNames`: Melatonine, Pure Creatine, C4 Original, …); S-57 validated the names against that shifted 10-product per-turn window, replaced the recommendation with the specialist holding message, and raised `hallucinated_product_name`. (A truly empty retrieval set would have disarmed the guard — `filterHallucinatedProductNames` returns early when `matchedProducts` is empty, `aiService.ts:3387`; the failure mode is a *rotated* window, not a missing one.) EV-025 509f4690 shows the sibling recommendation flow ending in `product_question_unanswered` on its price/flavor follow-up turn — the same alert as R16's 45247737.

The mandate is enforced against one guard out of six that can raise product alerts. It is bound per-guard rather than at the shared alert-creation layer, so the other five product-alert guards are not governed by it.

### 2. R6/R13: "Unavailable → say so (+ alternatives)" — saying so gets escalated

`shouldEscalateUncertainAnswer` (`uncertainAnswerFallbackGuard.ts:229-241`) fires on `negativeAvailabilityDetected` unless `hasMatchingProductsInContext` — i.e., unless this turn's retrieval returned products. The guard's own doc comment says the exemption exists because such replies are "the AI correctly following guidelines.catalog_integrity." But availability questions about products the store genuinely lacks (or that retrieval missed) are precisely the turns where `matchedProducts` is empty — so the honest negative R6 mandates is replaced with "Përshëndetje, do t'ju kthehemi së shpejti…" and escalated. EV-012 10946774 is the on-record instance: customer asked "a keni ndonje produkt ne ofert be" (any products on offer?), the AI answered "Nuk kemi oferta aktive për momentin." — compliant with R6 *and* with the orphan offers block's explicit instruction — and was escalated with `negative_availability_detected: true`. The rule and the guard are satisfiable simultaneously only when retrieval succeeds.

### 3. R15: usage escalation — correct rule, coin-flip execution

The rule itself is well-implemented (three guard variants + speculative-health guard). But candidate usage texts come from `matchedProducts` (processAIReply.ts:1995-1999), so whether a usage question is "answerable from the catalog's usage section" is decided by the same nondeterministic retrieval: EV-025 shows the identical question ("Sa her ne dite muna me perdor?") answered factually at 21:05 and 22:03 and escalated with alerts at 21:46 and 21:54 the same evening — the escalations *between* the successful answers, ruling out a config change. 14 of 20 dev alerts are conversation-terminal (EV-014 classification), so each false escalation is a lost conversation.

### 4. R14: post-purchase escalation — enforced, but fail-open as a unit

The pre-reply path implements R14 faithfully (fixed apology + alert, S-26/S-28), but the umbrella try/catch spanning `processAIReply.ts:1379-1948` catches any throw from *any* pre-reply path and proceeds to normal generation (DP-GPR-28) — silently dropping cancellation/refund/post-purchase escalations. R14 holds only while nothing in a 570-line block throws.

### 5. R12: order confirmation — the one rule biased in the safe direction

The 7-conjunct gate enforces "product questions ≠ confirmation" deterministically, but its failure asymmetries (missing confidence boost DP-GPR-16, swallowed catch DP-po-18) plus the eval model scoring every order confirmation 0.200 (Phase 4 Q4) mean errors forfeit orders/commission rather than fabricate them — a business-revenue bug wearing a safety costume.

| `ai_configs.custom_model_id` | replaces chat model (not vision) | 0/6 |
| `tenant_prompt_blocks`: enabled / content / sort_order on non-locked blocks | `updateTenantPromptBlock`, reset-to-default (`promptBlock.ts:176-224`) | **zero customization: `variants = 1` on all 13 keys** |
| Custom tenant-only blocks (`custom_` prefix, `prompt_block_id = NULL`) | `insertCustomTenantPromptBlock` (`promptBlock.ts:226-255`) | none observed |

**Locked-block force-sync:** the 6 locked blocks are self-healed to catalog `default_content` on **every `generateReply` call** (`aiService.ts:239-251` → `forceSyncLockedBlocksForTenant`, `promptBlock.ts:355-391`) — an UPDATE attempt per reply, introduced by migration 052 after exact-string syncs missed tenants. Locked content therefore cannot drift (but also races: two workers can assemble different guideline sets inside the cache-refill window, DP-pc-08).

**Drift potential — asymmetric and real:**

- **Non-locked blocks never resync.** Platform fixes to `messaging_style`, `discount_policy`, `product_usage_verbatim`, `follow_up_and_closing`, `recommendations`, `vision_product_images` reach tenants only via hand-written migrations with exact-string or manual syncs (041, 050, 056, 061, 064, 066, 067). The first tenant who customizes any of these permanently forks off the fix train — today's `variants = 1` uniformity is luck, not mechanism.
- **Catalog deactivation does not disable tenant rows** — proven twice: migration 056 had to disable `product_description_responses` manually, and `offers_promotions` (no such migration) is still enabled 6/6 (C-01).
- **The spec's delivery channel is per-tenant data.** Because business.md lives in `ai_configs.restrictions` rather than a locked block, onboarding a tenant without copying the array (the current state of 5/6 tenants) silently drops the entire rulebook — and there is no sync mechanism at all for restrictions.

## Hallucination/alert-contributing instructions

Evidence-tied observations on which prompt texts plausibly contribute to wrong answers, unnecessary alerts, or inconsistency:

1. **The catalog hidden-count note vs the name guard** — `aiService.ts:2111-2123` injects: "CRITICAL: If you recommended a product in a previous conversation turn and it is not shown in the current catalog section, that product IS in the catalog." This *correctly* instructs the model to trust its earlier recommendations across retrieval windows — and S-57 then punishes exactly that trust by validating names against the current window (fcd0af7e, EV-011). The instruction and the guard encode opposite beliefs about the same situation; the instruction is right and the guard is wrong.
2. **The orphan offers block** (C-01) — instructs answering offer questions from a section that never exists. Best case, the model says "no active offers" and risks the uncertain-answer guard (EV-012); worst case, the model treats the tenant's `Discounted price` lines or its own priors as the missing section and invents offer terms. 1,478 chars of pure liability in every prompt.
3. **Mandated deflection wording that matches escalation regexes** — `category_product_aggregation` (locked) mandates "note that you do not have that specific detail available," and `product_usage_verbatim` mandates "say you do not have that specific information available. A specialist will provide accurate guidance." The natural Albanian renderings ("nuk kemi informacion…", "nuk e kemi këtë të dhënë") are matched by `DEFLECTION_PATTERNS` (`uncertainAnswerFallbackGuard.ts:114-130`), and self-authored "specialist" sentences are caught by the usage-fallback fuzzy matcher (S-47, `processAIReply.ts:543-567`), which raises `usage_question_unanswered` even when it decides not to replace the text. The prompt teaches the model to speak in phrases the guards treat as failure signals.
4. **Price withholding + "only if it matches the catalog exactly"** — `price_currency_visibility` permits prices "only if it matches the catalog exactly," but when the price-intent classifier misses, the catalog section contains no prices at all, so a model answering a genuine price question can only source prices from history — which June's price guard then flagged against an empty/mismatched set (EV-011: correct €18.00 prices alerted, `failureReason:"no_catalog_prices"`). Note: that failure string no longer exists in source; the current guard fails open on an empty price set (`priceConsistencyGuard.ts:141`) — the June incidents document a since-churned guard variant, itself evidence of the reactive tuning pattern.
5. **Verbatim-usage extraction vs `max_tokens: 768` and triple-brevity** — `product_usage_verbatim` demands word-for-word reproduction of usage text while three brevity instructions and a 768-token cap (`aiService.ts:4122`) push against completeness; a truncated or paraphrased extraction then reads as "unanswered" to `isUsageQuestionUnanswered` (whose prompt is fail-closed: "WHEN IN DOUBT → return is_unanswered: true", `aiService.ts:2330-2387`). Plausible contributor to the EV-025 usage coin-flips alongside retrieval variance.
6. **Follow-up ban vs mandated invitations** (C-04/C-05) — the model is simultaneously told to never produce "ask if you want anything" phrasing and, in two blocks, to produce it. Whichever way it resolves, S-54's invitation-strip can then remove a mandated sentence or the eval model can penalize a compliant one — low-grade inconsistency pressure on every no-match and options-exhausted turn.
7. **The restrictions gap itself** (EV-029) — five tenants' models operate without R1's `[NO_REPLY]` protocol, R4's comparison format, or R16/R17's "answer directly" reinforcement. Cross-tenant behavioral inconsistency is thus configured, not emergent: the same customer question is governed by materially different prompts depending on tenant — while all six tenants share identical guards, thresholds, and alert taxonomy.
