# Phase 14 — Production Readiness Audit

> **Evidence base:** Grounded in source code (file:line), the dev/staging database, live-replay experiments (Phase 10), and the confirmed root causes of Phase 11. Dev data demonstrates mechanisms, not production incidence rates. See appendix-A-evidence-log.md.

This phase reads the confirmed ledger (Phase 11, 22 CONFIRMED + 3 WEAKENED root causes), the component registry (Phase 9, 152 findings), the runtime ground truth (Phase 10), and the architecture review (Phase 12) through a single lens: **can this system be operated at the scale the business model implies — thousands of concurrent tenants, millions of conversations/month, continuous deploy — without a human watching every message?** The answer is assembled from mechanisms that are individually verified but whose *production incidence was never measured*; the dev snapshot (6 tenants / 46 conversations / 374 messages / 617 products, **0 channels**, EV-038) demonstrates how each defect fires, not how often it would.

The through-line: Hillside is architected as a **single-instance, single-process, single-Redis, single-model-provider** system whose per-message hot path is **18–25 serialized stochastic OpenAI calls** (C-121, Phase 10 ground truth), with **no circuit breakers, no DLQ, no decision observability, and a CI gate that runs no tests and does not gate deploy** (RC-23). Every scaling axis and every failure axis converges on the same small number of shared singletons. Observations only — no fixes proposed here.

## Throughput & scaling limits

The binding throughput constraint is not Postgres or Redis capacity — it is the **per-message OpenAI fan-out** and the **single-process topology** that hosts it. At the target scale each of the following becomes a hard ceiling.

**Workers run in-process with the HTTP API (C-130, `server.ts:5-18`; RC — seed "Workers run IN-PROCESS").** All five BullMQ workers (`webhook`, `ai`/`ai.reply`, `notifications`, `finetuning`, `default`) plus Express plus the Socket.IO server share one Node process on a single 1-vCPU / 2-GB droplet. Production compose dials AI concurrency to **2** (`docker-compose.prod.yml`; seed "prod compose dials concurrency to 3/2/1/1/1"), so the **system-wide ceiling is ~2 concurrent AI replies** regardless of tenant count. There is no separate worker deployment and no replica set — scaling is vertical-only. At thousands of concurrent tenants this is not a bottleneck, it is a wall: a single busy tenant's burst monopolizes both AI slots and starves every other tenant platform-wide.

**Per-tenant fairness cap (8) is simultaneously inert and hazardous (C-133, `processAIReply.ts:1093-1096`; DP-iq-19/20).** The per-tenant Redis slot limit is `AI_MAX_CONCURRENT_PER_TENANT=8` (Phase 10 live default), but prod AI concurrency is **2**. The cap therefore *never engages* on a single instance — a noisy tenant already starves everyone with 2 in-flight jobs before the cap of 8 is reachable. When it *does* engage (at multi-instance scale) it does not shed or queue fairly; it **busy-loops re-adding fresh delayed jobs every ~3s** (C-79, self-reschedule), converting a fairness mechanism into a retry amplifier. The fairness primitive is mis-sized against the concurrency it is meant to ration.

**18–25 serialized LLM calls per message; ~70 worst case (C-121, `processAIReply.ts:1373-3529`; seed "worst-case fan-out 18–25+").** The dominant latency and cost term is a deep, mostly-serialized classifier chain around one unconstrained generation (Phase 12 thesis). The single largest multiplicative term is `hasAssistantAskedOrderClosingInConversation` — an **uncached per-assistant-message LLM classifier invoked twice per job** over a re-fetched 40-message window (~40 calls, C-126, `processAIReply.ts:2597`), growing with conversation depth. `classifyNewOrderSignal` + `detectOrderAffirmationIntent` each run twice per job on overlapping context with no batching or per-conversation cache (C-127). Only 2 of ~30 classifier sites honor a dedicated model env var (C-103); the rest ride `OPENAI_CHAT_MODEL` = live **gpt-4o** (Phase 10 config) — the full, expensive model — for every boolean decision. At millions of conversations/month this is call-count-dominated spend (C-108: `completion.usage` is discarded on every call, so there is **zero per-conversation cost visibility** on a usage-billed product).

**Unconditional 8s debounce floor on every first reply (C-123, `processInboundMessage.ts:886-907`; RC-05, DP-iq-16).** Every first reply eats a fixed 8s delayed-debounce before any LLM work begins; realistic first-response ≈ 8s + 10–15s generation ≈ **18–23s**. This floor is per-message and does not amortize. The same debounce path performs an **O(queue-depth) scan** — it deserializes *every tenant's* pending `ai.reply` jobs into memory on every inbound and then removes at most one (C-134, `processInboundMessage.ts:886-892`; DP-iq-17). The scan cost grows precisely as the platform saturates: at high queue depth every inbound pays a full-queue materialization, a super-linear degradation exactly when headroom is scarcest.

**Connection pool is a shared ~8-instance ceiling and a hot-path bottleneck (C-131, `db/pool.ts:53-58`).** `PG_POOL_MAX=10` is shared by the API and all workers in one process. Each reply performs a **double 40-message history fetch + up to 13 discrete `pool.connect()` transactions + multi-source retrieval SQL** (C-128, `processAIReply.ts:1338-3575`), so a single in-flight reply can hold many of the 10 connections serially. Postgres `max_connections=80` implies a **horizontal ceiling of roughly 8 app instances** before the database refuses connections — and the pool is not tuned per role (API vs worker), so read-heavy API traffic and connection-hungry reply jobs contend for the same 10 slots.

**Global HNSW recall degrades monotonically with platform success (C-132, `db/models/product.ts:721-729`; SC3; DP-retrieval-08).** The vector index is global with a *tenant post-filter*, not a per-tenant index. As total cross-tenant product count grows, a small tenant's true matches get crowded out of the candidate set; the only mitigation is a fixed 500-candidate `ef_search` ceiling reached via an **adaptive double-pass that fires on nearly every query for small/new tenants** (C-125, `product.ts:804-814`). Recall therefore *degrades as the platform grows* — the failure mode strengthens with commercial success. Phase 10 (EV-043) confirms this is **dormant at dev scale**: the planner cost-prefers an exact seq scan at 617 rows and only 1 cross-tenant product exists, so the crowding mechanism is doubly unrealized today. It is a design-time scaling concern, not a runtime-observed one — but it activates precisely in the target regime.

**Net throughput picture.** The scaling limits are not independent — they are the same singleton viewed from different angles. One process caps concurrency at 2; the shared pool caps horizontal fan-out at ~8 instances; the 18–25-call fan-out caps per-slot throughput; the 8s debounce sets a latency floor; the O(queue-depth) scan degrades under exactly the load that would justify scaling. Collapsing the fan-out (Phase 12 recommendation) is simultaneously the throughput, latency, and cost fix; nothing else moves all three.

## Single points of failure & cascading risks

Four hard single points of failure sit on the critical path, plus a class of non-atomic writes whose failure cascades into billing and customer-visible state. **SPOF count: 4.**

**SPOF 1 — Single application process (C-130, `server.ts:5-18`).** Express + all five workers + Socket.IO in one process on one droplet. A crash, OOM, or a `SIGKILL`-truncated deploy (see Deployment) takes down ingestion, AI replies, notifications, cron reconciles, and the real-time socket feed *simultaneously*. There is no replica to absorb the failure and no separate worker fleet to keep draining the queue while the API restarts.

**SPOF 2 — Single Redis, noeviction, co-locating everything (C-135, `docker-compose.prod.yml:50-53`; SC6; EV-040).** One 192-MB `maxmemory` Redis with `maxmemory-policy=noeviction` holds **BullMQ queue state, the prompt-assembly caches, the per-conversation locks, the rate-limit counters, the self-echo registry, and the Socket.IO adapter pub/sub** — every hot-path primitive. Two compounding hazards: (a) `evaluateConversationUseCase` and the failed-job sets use `removeOnFail:false` → **unbounded growth** (EV-042: ~79 failed jobs already retained, never trimmed); (b) at the 192-MB ceiling, `noeviction` means every `SET`/`INCR`/`add` **errors** rather than evicting — and because reply-critical Redis calls are *not error-guarded* (C-54, `aiService.ts:203-304`: a flap throws and fails the whole `ai.reply` job), a full Redis silently converts into platform-wide reply silence. Phase 10 notes `maxmemory=0` in the *dev* instance (EV-040), so the eviction valve is currently inert — but the prod overlay pins 192 MB, arming it. A single Redis stall is a total-pipeline stall with no eviction relief and no fail-open on the reply path.

**SPOF 3 — Single OpenAI provider with fail-open/fail-closed asymmetry (RC-19, RC-01; C-65/C-66/C-121).** There is one model provider and no fallback. The 18–25 serialized calls each inherit the SDK's **60s timeout × (1+3 retries) ≈ 240s** with no per-classifier abort (C-66, C-96, `openaiClient.ts:15-29`) and **no circuit breaker** (C-65). Provider degradation does not degrade gracefully — it degrades *incoherently*: the entire pre-reply escalation subsystem is fail-open under one umbrella catch (RC-19, `processAIReply.ts:~1383-1948` → `console.warn "...continuing normal flow"`), so a **refund/cancellation demand gets a normal sales reply, no alert, no pause, no retry**; meanwhile the one fail-closed gate (RC-01, `productInformationGapService.ts:105`) **escalates every product question** (live replay: 8/8 on a correctly-answerable availability question, EV-044). The audit counted **6 fail-closed / 79 fail-open / 32 silent-drop** sites (Phase 12 reliability sub-audit). So an OpenAI incident does not produce a clean outage — it produces a mix of wrong-class replies, false escalations, and silent forfeitures, with no single signal that anything is wrong. AI-path errors also never reach Sentry (C-110, `instrument.ts:27-37`: 0 `captureException` in `jobs/`), so this SPOF fails *invisibly*.

**SPOF 4 — Single Postgres + shared pool (C-131, `db/pool.ts:53-58`).** One database instance, one 10-connection pool shared across API and workers (see Throughput). A pool exhaustion event (13 transactions/reply × 2 concurrent replies + API traffic) stalls both the reply path and the API with no read-replica to shed reads onto.

**Cascading risk — non-atomic post-send writes (RC-20, RC-21; C-47/C-81/C-152).** The pipeline sends the outbound message *before* it persists, then performs a sequence of non-idempotent writes (persist message, insert alerts, INCR counters, create draft order, log analytics) with no transactional envelope:
- **Crash-after-send on FB/IG/Viber** re-runs the whole job on BullMQ retry and **collides on the globally-UNIQUE `external_message_id`** (RC-20; `012_create_messages.sql:5`, C-47) → the retry dead-letters, losing the alert/analytics/billing/draft-order side effects **for a reply the customer already received**. On WhatsApp (null id) the retry inserts a **duplicate row with a fresh temp-0.3 generation ≠ the delivered text**.
- **Throw between persist and enqueue** (RC-21, `processInboundMessage.ts`) leaves a stored, inbox-visible message with **no `ai.reply` job ever created** — artifact-free silence; on retry the global dedup finds the row and returns before enqueue. Enqueue also runs *after* `res.sendStatus(200)`, so an enqueue failure is only `console.error`'d and the platform never redelivers (C-78, `processInboundMessage.ts:886-907`).
- **Deploy-injected instance of the same class:** `SHUTDOWN_TIMEOUT_MS=25000` exceeds Docker's default 10s grace with no `stop_grace_period` (C-152, `server.ts:41`), so a deploy `SIGKILL`s in-flight `ai.reply` jobs mid-send → the same non-idempotent retry path fires on every continuous deploy.

These are not classic SPOFs but they share the SPOFs' property: **there is no atomic boundary**, so a single mid-pipeline fault cascades into permanently-inconsistent customer, alert, and billing state. Billing specifically cannot be trusted to reproduce (RC-22: `NOW()`-relative commission window post-send; RC-24: IG/FB self-echo misclassified as human on any Redis registry miss silently zeroes use-case fees).

## Queue saturation / retry storms / backpressure

The queueing layer has **no backpressure, no shedding, no priority, and no dead-letter path** (SC7, C-136, `aiQueue.ts:10-14`). Under the target load, the failure mode is not a clean overload signal — it is silent amplification.

**Self-rescheduling adds FRESH jobs → unbounded retry budget (C-79, `processAIReply.ts:1164-1171`; seed "Self-rescheduling adds FRESH jobs").** When the pipeline reschedules (fairness-cap contention, human-hold wait, lock contention) it enqueues a *new* job with a *reset* attempts counter rather than re-delaying the existing one. BullMQ's `attempts:3` ceiling is therefore **not a real bound** — a conversation can be reprocessed indefinitely across reschedules, and each reschedule re-runs non-idempotent side effects (the rate counter INCRs per *attempt* before the gates, RC-18/C-83, so retries and stale jobs **burn the 25/h budget on phantom increments** and strand a legitimately-busy conversation in a persistent `ai_paused`). Under load this is a retry storm generator: contention creates fresh jobs, fresh jobs deepen the queue, deeper queues increase the O(queue-depth) debounce scan cost (C-134), which slows every inbound, which increases contention.

**No DLQ anywhere; the dead-letter is customer-invisible (C-87, `jobs/failureHandler.ts`; SC — seed "no DLQ anywhere").** An exhausted `ai.reply` job produces **no alert and no reply** — the customer simply never hears back, with no operational signal. The `notifications` queue that would carry such an alert has **zero producers — it is a dead queue** (C-87; seed "notifications queue has NO producers"). Worse, `failureHandler` **misclassifies stall-killed jobs as retryable** (C-88), so the exhaustion alert that would fire on a terminal failure never fires. The dominant anti-pattern (Phase 9 reliability): *"return success on failure"* — swallowed throws (C-89: 3 verified sites including the purchase-intent throw at `processAIReply.ts:3831-3837`), non-throwing sends (C-90: channel send wraps even rate-limit errors into `{success:false}`), and fail-open transactions all conspire so **BullMQ almost never sees a real failure** — which is exactly why the absence of a DLQ has gone unnoticed. There is no safety net because the system is engineered so the net is never triggered.

**The 79 retained failed jobs are the visible residue (EV-042).** Runtime inventory found **~79 failed jobs retained with no auto-trim**: `webhook` 30 (IDs 5, 17–46, 786–787), `default` 20, `message.inbound` 16 (contiguous 3–18), `ai` 7, `ai.reply` 3, `product.embedding` 3. These accumulate in the same 192-MB noeviction Redis (SPOF 2) — a slow memory leak that, at the target failed-rate, walks the instance toward the ceiling where every queue write errors. The contiguous low-ID `webhook`/`message.inbound` sets are early-dev ingestion failures retained indefinitely; nothing sweeps them.

**`offerEmbeddingReconcileFast` fails on ~every run (EV-042; seed).** All **20** `default`-queue failures are `repeat:offerEmbeddingReconcileFast:*` iterations — a scheduled reconcile job **failing on nearly every run**. This is an undocumented per-minute/2-minute "fast lane" cron (seed "7 cron schedulers incl. undocumented per-minute/2-minute reconcile fast lanes") multiplexed onto the concurrency-1 `default` queue alongside live product embeds (C-137, `docker-compose.prod.yml:68-70`). A slow or failing reconcile **blocks the embed a new product needs**, which triggers more zero-hit self-heal reconciles — a self-sustaining contention loop on the queue that feeds retrieval. At scale (continuous product imports across thousands of tenants) this queue is structurally under-provisioned and already failing at dev scale.

**No backpressure or load-shedding (C-136).** A single FIFO `ai` queue × concurrency 2 × 8s delay has **no depth-based shedding, no priority lane, no admission control**. A traffic burst grows queue depth unbounded before any alert (there are no queue-depth metrics — C-112: AI decisions emit free-text logs only, no counters). Combined with the fresh-attempt reschedule amplifier and the O(queue-depth) debounce scan, a burst does not degrade gracefully — it compounds. The monthly billing snapshot adds a correctness hazard under retry: it uses a **non-upsert INSERT under `attempts:3`** (C-82, `commissionReport.ts:49-68`), so a transient failure produces **duplicate commission reports**.

## Security

Application-level tenant isolation (no RLS, no schema-per-tenant — CLAUDE.md §5) holds on the join graph in dev data (EV-038: 0 cross-tenant mismatches) but is undermined at the **webhook ingestion seam**, where tenant resolution happens without a JWT.

**SEC-2 — unscoped channel→tenant bind (RC-09, C-115, `db/models/channel.ts:119-128`; DP-iq-07).** `findChannelByTypeAndExternalId` is the **sole webhook tenant resolver** and it has **no tenant scope, no `ORDER BY`, and a bare `LIMIT 1`**. The `channels` UNIQUE key is `(tenant_id, type, external_id)` — it *includes* `tenant_id`, so there is **no global `(type, external_id)` guard** and the DB permits two tenants to bind the same messaging account (EV-038, schema-confirmed). If a page/number is dual-connected (or re-onboarded to a second tenant), an inbound message — and the AI reply, catalog, persona, and **commission** it generates — routes to an **arbitrary tenant**. Phase 10 marks this **latent, not observed**: the dev `channels` table is empty (0 rows, EV-038), so it cannot manifest in data here and rests on code-reading. At the target scale (thousands of tenants, high onboarding churn, agencies managing multiple businesses) dual-connection is a realistic operational event, and this is the highest-severity isolation defect in the ledger.

**Global inbound dedup (C-114, `db/models/message.ts:290-298`; DP-iq-06).** `findMessageIdByExternalMessageId` also has no tenant/channel scope. Phase 9 (WF-F correction) downgrades the cross-tenant-collision harm to near-zero because platform IDs are namespaced — but the real S1 harm remains: a collision **silently drops a paying tenant's inbound** and leaks cross-tenant existence. The `external_message_id UNIQUE` being global (C-47) is the same column that dead-letters delivered replies on retry (RC-20).

**Conversation-scope history query (C-116, `db/models/message.ts:304-321`; SEC-3).** The AI history loader is **conversation-scoped only** — it injects the 40-message window into the prompt with **zero tenant re-verification**, trusting upstream resolution entirely. Phase 9 rates this S2 defense-in-depth (internally-resolved `gen_random_uuid`, never attacker-supplied — C-46) **but S1 if reached via SEC-2**: if a webhook is misrouted, the history loader will faithfully assemble another tenant's conversation into the prompt with no second check.

**Prompt-injection surface (C-117, `aiService.ts:3019-3047`; SEC-4; DP-GPR-27).** Customer text is interpolated **unsanitized** into instruction-framed prompt strings (`Customer replied to: '…'`, edit-hint blocks). On an *autonomous, commissionable* agent that can quote prices, apply discounts, and confirm orders, a crafted message can attempt to steer pricing/discount/order confirmation. There is no escaping, delimiter-hardening, or injection guard. RC-07/RC-22 compound the exposure: order-info updates mutate the order *before* the send precheck (DP-GPR-27), so a successful steer can silently alter an order.

**PII in alerts and logs (C-113/C-118, `aiService.ts:744-4280`; SEC-5, OBS-7).** Raw customer text — names, phones, addresses, health context — is logged in **cleartext to stdout at ≥4 sites with no redaction layer**, and `ai_alerts` rows carry customer content. This is a GDPR/retention exposure on an EU-registered company (Hillside L.L.C., Kosovo) serving EU customers. Forensic residue makes it worse: pre-2026-06-23 alert `details` are null/unclassifiable and a 06-27 mojibake regression corrupted stored fallback text (seed forensics; SEC-5). At millions of conversations/month the cleartext-PII log volume alone is a compliance and blast-radius problem.

**Admin boundaries — verified correct (C-120, `authenticateAdmin.ts:17-48`; SEC-7, positive).** The one *positive* security finding: the platform-admin auth boundary rejects a business token with 403 and returns a distinct 503 when the admin JWT is unconfigured — no privilege-escalation gap. Note two operational caveats: `ADMIN_KEY` is **unset** in the live env (EV — Phase 10 config table), so the Bull Board / admin-key path has no key configured; and channel-token AES-256-GCM is cryptographically sound but has **no key id/version** (C-119), making rotation a big-bang re-encrypt and a decryption failure a *silent non-delivery* (send never throws).

## Missing operational safeguards

The safeguards a system needs to run unattended at scale are largely absent. This is the gap between "works in a demo" and "survives production."

**No circuit breakers (C-65, C-66; `openaiClient.ts:15-29`; `processAIReply.ts:1942-1948`).** Nothing trips when OpenAI slows or errors. The 18–25 serialized calls each wait up to ~240s (60s × 4) with no per-classifier latency budget and no breaker to fast-fail after N consecutive failures. A degraded provider does not shed load — it holds worker slots and conversation locks for minutes (C-90: the outbound limiter busy-polls up to 60s *inside the conversation lock + worker slot*; two stalls saturate the concurrency-2 pool). Adjacent guards on the *same event* fail in *opposite directions* with no breaker to mediate (C-65: gap assessor fail-closed vs attribute/pre-reply fail-open).

**No graceful degradation (RC-19, RC-01, Phase 12 reliability).** There is no "AI unavailable → templated holding reply + escalate" fallback. When the model path fails, the outcome is determined by *which catch happens to wrap the failing call*: fail-open (wrong-class reply, RC-19), fail-closed (false escalation, RC-01), or silent-drop (no reply, C-89). The floor of the system under provider failure is *silence or a wrong-class reply*, not a safe degraded mode.

**No output validation contract (C-62, `aiService.ts:133-143`; T1).** There is **no structured-output contract anywhere** — all ~30–33 classifier calls rely on `response_format: json_object` + hand-written parsing, with non-uniform failure handling across sites (C-64: fail-open/closed/throw mix) and **scale-guessing** on numeric outputs (C-63: `>1? /100` collapses an overconfident 0–1 score by 100×). The main customer generation has **no `response_format` and no seed** (RC-03, C-22, `aiService.ts:4118-4124`) and **ignores `finish_reason`** — silent truncation at `max_tokens=768` (C-97). There is no facts-declaration contract, so grounding is checked by free-prose parsing against the wrong reference set (RC-02).

**No auto-resume / no lifecycle exits (RC-14; C-14/C-15/C-16).** Every pause is a permanent silent dead-end: `ai_paused`, rate-limit pauses, and `human_override_until` have **no automatic re-enable** — exits exist only via a human toggle or an alert resolved with explicit `resume_ai:true`. Phase 4 (Q7) found **14/20 alerts fire on the conversation's final turn**, and Phase 5 catalogued **six dead-end states** (AI-PAUSED, RATE-LIMITED-PAUSED, ALERT-RESOLVED-WITHOUT-RESUME, SILENT-ACTIVE, HOLD-ANOMALY-SILENCE, REOPENED-BUT-PAUSED) with no exit transitions. Unattended, a paused conversation stays silent forever; the frontend even manufactures dead-end #3 as the *default* Close-alert action (C-16, `AIAlertsPage.tsx:330-332`).

**No observability substrate (C-107/C-108/C-109/C-110/C-112).** The assembled system prompt — the actual LLM input — is **never logged or persisted** (C-107), so no divergence can be reconstructed post-hoc. Token/cost/latency is **never captured** on a usage-billed product (C-108). `traceId` reaches only 2/101 job log lines and `aiService` never receives it (C-109), so a message's journey cannot be stitched across concurrent workers. AI-path errors never reach Sentry (C-110). No metrics/counters exist for any AI decision — escalation, guard-strip, `semanticSkipped`, `[NO_REPLY]` rates are free-text only and undetectable as trends (C-112). "Why did this escalate?" is currently unanswerable — it is archaeology.

## Input/output validation gaps

**Untrusted ingestion has zero schema validation (C-11, `processInboundMessage.ts:434-455`; B5).** The webhook surface — the one endpoint reachable by an untrusted third party — is **hand-parsed, first-element-only, with no Zod schema** (contrast: every authenticated CRM route validates). Consequences already catalogued in the seed: Viber verifies nothing on handshake/receipt events; **malformed Meta payloads are silently dropped in the worker; malformed Viber payloads retry to permanent failure**; the webhook timestamp-skew check **falls back to `Date.now()` and passes when no timestamp is present** (RC-11, C-94 — replay risk), while a *valid-but-late* payload is 403'd and Meta redelivers the same stale timestamp forever (permanent silence). At scale the ingestion surface is both the least-validated and the most-exposed.

**Express 5 read-only query/params breaks coerced validation (C-07, `middleware/validate.ts:38-44`; B1).** The validate middleware never rewrites `req.query`/`req.params` (read-only in Express 5) — coerced values land only on `req.validated`, so any handler reading `req.query` directly gets **un-coerced strings**. This is a silent correctness gap that widens as new endpoints are added by developers who assume validation mutated the request.

**Unbounded list endpoints (C-10, `chatbotControlController.ts:71-80`; B4).** The paused-conversations list (and other list endpoints with inconsistent envelope shapes) returns an **unbounded** result set with no pagination — fine at 46 conversations, a memory and latency hazard at millions. The AI global on/off toggle has **no validation and no desired-state contract** (C-08, `chatbotControlController.ts:21-41`) — blind flips race, and the toggle mutates `ai_configs` **without clearing the `ai_config:` cache** (C-55), so a 900s delete-only cache window can serve stale AI state.

**Output side: no contract, silent truncation, no idempotency markers on side effects.** Covered above (C-62/C-63/C-64/C-97) — the through-line is that neither the boundary *in* (webhook) nor the boundary *out* (LLM output → business action) is validated against a schema. Error responses also leak: `sendError` returns the raw error payload for non-Error throws **in all environments** (C-13, `utils/response.ts:28-36`).

## Deployment & rollback risks

Continuous deploy is the stated operating mode, and the deploy path is the least safe part of the system.

**Staging deploy is ungated on CI (C-149, `.github/workflows/deploy.yml:3-24`; RC-23, T2).** `deploy.yml`'s `deploy-staging` triggers on **push-to-main with no `needs:` and no `workflow_run:` gate on CI** — it is a *separate workflow that runs concurrently with, and independent of, `ci.yml`*. A commit that fails typecheck, build, or lint **still fires the staging deploy**. Production is gated on `v*` tags, but staging (the environment nearest to customers in a fast-iteration shop) can be broken-and-live while CI is still red. Verified separate workflows, no gate (Phase 10 confirms).

**CI never runs the tests (C-145/C-146/C-147, `.github/workflows/ci.yml:72`; RC-23).** `ci.yml` runs typecheck + build + migration smoke-test + health check + lint but **never `npm test`** — the token `test` appears only as `NODE_ENV`. Phase 10 proved the suite is real and green: **548 tests / 75 suites / 0 fail, fully offline in ~6s** (EV-043). So 548 assertions protect nothing at the gate. The coverage is also *inverted* (C-147): every verified failure locus (`processAIReply`, queue dedup, retrieval race, billing snapshot) has **0 tests**, while the tested slice is exactly the deterministic, side-effect-free leaf helpers. There is **no AI eval/regression harness** and the smoke path boots with a placeholder key and only polls `/api/health` — no message ever traverses `processAIReply` (C-146). The frontend has **no test runner at all** (C-148). On a continuous-deploy cadence, this means every change to the billing-critical guard pipeline ships unregressed.

**Migrations: non-atomic, forward-only, duplicate 062, out of order (C-150/C-151, `db/migrate.ts`; RC-23; EV-037).** The migration runner sorts by **full filename lexicographically** with a **per-file `BEGIN/COMMIT` (not atomic across files), no `pg_advisory_lock`, and no down migrations** (C-151). Migrations run **at deploy AND every container boot** with no advisory lock → a TOCTOU where two boots race the same migration. **Duplicate ordinals 062–065 each exist twice** (offers branch + guidelines branch, EV-037); `065_offers` (id 69) applied a **day before** `063_catalog_grounding` (id 70) — the numeric prefix is no longer an ordering contract (C-150). A mid-sequence throw leaves the schema **half-migrated with no rollback path**. Because prompt behavior is versioned *as* migrations (C-142: 19 prompt-mutating migrations, force-sync overwrites), a partial apply can leave AI behavior in an undefined state — and the orphan `offers_promotions` block that injects a phantom "Active offers" section into 6/6 tenant prompts (RC-26, C-25) is exactly how an un-allowlisted migration branch corrupted the live prompt.

**No safe rollback under continuous deploy (C-152, `server.ts:41`).** Single-instance replace-in-place with `SHUTDOWN_TIMEOUT_MS=25000` but **no `stop_grace_period`**, so Docker's 10s window truncates the drain and **`SIGKILL`s in-flight `ai.reply` jobs** that then retry non-idempotently (duplicate spend/alerts on FB/IG/Viber, a re-generated ≠-delivered reply on WhatsApp — RC-20). Forward-only migrations mean a bad deploy **cannot be rolled back by redeploying the previous image** if it applied a schema change. Every continuous deploy is therefore a potential Issue-1 divergence injector and an unrecoverable-forward commitment.
