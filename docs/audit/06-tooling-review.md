# Phase 6 — Tooling Architecture Review

> **Evidence base:** All findings below are grounded in source code (file:line cited, verified against branch `main`, commit `a8ceb15`) and, where noted, the dev/staging database (6 tenants / 46 conversations / 374 messages / 617 products / 20 ai_alerts). Dev data demonstrates mechanisms, not production incidence rates. Step ids (S-NN) refer to `02-execution-trace.md`; DP-nn ids to the Decision Point Register in `03-divergence-analysis.md`; EV-nnn ids to `appendix-A-evidence-log.md`. Dispositions here are the mandated Phase 6 output; implementation specifics belong to Phase 16.

**Framing — there is no tool-use architecture to review in the conventional sense.** This system has **no function-calling / tool-selection layer**: no OpenAI `tools`/`function_call` parameter appears at any call site, no site uses `json_schema` structured outputs, `seed`, or `logprobs` (classifier census, `02-execution-trace.md`; mapper `classifiers.md`). The LLM never chooses a tool. The de-facto "tooling catalog" is therefore: **33 in-pipeline classifier/guard/detector `chat.completions.create` call sites** (everything except the main reply completion at `aiService.ts:4118-4124`), **1 embeddings call site** reached by 4 pathways, and the **deterministic helpers** (price regex filter, reply strippers/sanitizers, fusion retrieval). All "routing" is deterministic orchestration code in `processAIReply.ts` / `aiService.ts` deciding *whether to invoke* an LLM call and *what to do with its JSON verdict*. This review catalogs those calls as if they were tools — because functionally they are: each is a single-purpose model invocation whose output gates a pipeline branch.

## Routing analysis

**All routing is deterministic code gating LLM calls.** No LLM ever selects the next tool; orchestration in `processAIReply.ts`/`aiService.ts` decides which classifier to invoke (gate) and branches on its JSON (verdict). Each routing decision is therefore two-layered: a cheap-but-brittle deterministic gate, then (sometimes) a costly-but-stochastic LLM verdict. Where the *gate* misses, the LLM never runs; where the *verdict* misses, execution lands on a concrete wrong branch:

| Routing decision | Gate type | Verdict type | Misroute → where execution goes | Evidence |
|---|---|---|---|---|
| Pre-reply escalation (cancel/refund/wrong-product/post-purchase) | none / regex cue (`hasPostPurchaseIssueCue` for #6 only) | LLM conf > 0.8 (boosted, DP-GPR-16) | False positive → canned ack + AI pause on a sales conversation; false negative (or any transport error, DP-GPR-28) → refund demand answered with a normal sales pitch, no alert | S-23/S-24/S-26/S-28 |
| Order-info update | none (runs unless new-order/affirmation) | LLM conf > 0.82 (boosted) | False positive → **order row UPDATEd** with wrong customer fields before the send precheck | DP-GPR-26/27, S-29 |
| Category-shopping intent | **regex only** (`hasCategoryShoppingIntent`) | none | Regex hit + tag match → **semantic retrieval source silently dropped** for the turn → wrong/narrower product set → downstream guard false positives | DP-retrieval-06, S-35 |
| Attribute-question routing | regex fast-path → LLM (#9) | LLM multi-field | is_attribute_question true → routes into the gap path (S-48) whose assessor is **fail-closed** — a routing misfire converts an answerable turn into holding+pause+alert | DP-gg-14/16, DP-retrieval-16 |
| Other-options ("what else?") | length/affirmation pre-screen → LLM (#26) | LLM | True → wide category search, persisted-anchor resolver skipped; false negative → stays on narrow retrieval and can miss the catalog breadth | S-36 |
| Contextual follow-up (empty retrieval) | heuristic ∥ LLM (#27, `\|\|` short-circuit) | LLM | Both miss → **fail-closed denial** of products the AI just recommended | DP-retrieval-15, Trace 3 |
| Usage question | none → LLM (#13, kw fallback) | LLM | False positive → usage-unanswered/health guards run on a non-usage turn (over-escalation); false negative → health guard never runs (its precondition, processAIReply.ts:2509) | DP-gg-09/19 |
| Image request | regex pre-screen (`mightBeImageRequest`) → LLM (#28) | LLM | Regex miss → no images ever considered; LLM null → silently no images | DP-gg-30 |
| Language | marker heuristic → LLM (#1) | LLM | Miss → `'sq'` default — an English-only customer can receive Albanian holding messages | DP-GPR-14/DP-pc-18 |
| Draft-order gate | 7-conjunct deterministic gate over LLM outputs (#8, #4, #5) | LLM ×3 | Any conjunct stochastically false → silent no-order (no signal, DP-po-30); threshold-adjacent score → coin-flip commission | S-69/S-70 |

The pattern across rows: **cheap gates are brittle in the miss direction (feature silently never runs), LLM verdicts are brittle in both directions (stochastic), and the two worst destinations are the fail-closed gap path (over-escalation) and the semantic-drop/anchor-loss retrieval states (wrong answers that the guards then punish).**

## Failure-mode analysis

The five mandated failure modes, mapped to register rows and dev evidence:

**1. Wrong tool called (misroute).** The category-intent regex silently drops the semantic retrieval source (DP-retrieval-06) — the turn is served by the wrong retrieval "tool". Attribute-intent misfires route answerable questions into the fail-closed gap assessor (DP-gg-14 destination; dev misfire `missing_info: ["ma shum"]`). Boosted pre-reply detectors (DP-GPR-16) route borderline messages into cancellation/refund escalation at manufactured confidence. Echo misclassification (DP-iq-12) routes the AI's own reply into the human-agent path, killing use-case billing.

**2. Unnecessary calls.** Worst-case **18–25+ LLM calls per customer message**, mostly serialized (census, `02-execution-trace.md`). Concrete redundancies: #4 and #5 each called twice per turn on the same text (processAIReply.ts:1593-1594 and :3528-3531); #18 called once **per assistant message in a history loop** when regex misses (:744-749); #17 exists only to veto #22's known false flags (:2734-2742); #1 called for texts the heuristic already resolves ambiguously-enough; four reply-shape classifiers (#16–#19) serially interrogate the same draft string.

**3. Required call skipped.** DP-po-18: the purchase-intent throw is swallowed at the processAIReply.ts:3831 catch (try opens :3510) — no retry, no alert, silent order + 5% commission forfeiture on a green job. DP-gg-31: the full-catalog fallback empties `matchedProducts`, silently disabling the entire hallucination-guard suite exactly when retrieval failed (dev: "Mass Gainer Pro" sent and sold unguarded in 6 conversations, Ph-4 #4). DP-GPR-28: one transport error inside the umbrella try/catch (processAIReply.ts:1379-1948) skips *all remaining* pre-reply detectors for the turn. DP-iq-15: a throw between message persist and `ai.reply` enqueue skips the entire pipeline permanently (global dedup blocks the retry). #22 returning null skips quality evaluation with no record.

**4. Hallucination instead of a tool call.** There is **no catalog-truth tool available at generation time** — the model answers prices/availability from whatever product context retrieval injected into the prompt. When retrieval misses (keyword-less follow-ups), the model correctly falls back on conversation memory — and the guards then misfire against the empty retrieval set: all 3 dev "hallucination" alerts are this shape, flagging replies verifiably correct against active catalog rows (EV-011/013/015; Traces 1–3). The one genuine near-hallucination in dev data — "Optimum Nutrition Gold Standard Whey" inexactly naming then-active "Gold standard whey" rows — went out precisely because the guard suite was disabled (mode 3). The system's answer to hallucination is post-hoc filtering of the reply rather than giving the model a grounded lookup; Phase 3 identified this inversion as the central mechanism.

**5. LLM where deterministic logic fits.** #20 follow-up-invitation: the LLM verdict is unactionable unless the deterministic regex independently finds the sentence (DP-gg-23) — the regex alone is the whole capability. #24/#25 price/discount question detection: the 30-item lexical fallback (aiService.ts:1293-1328) already encodes the domain vocabulary the LLM is asked to detect. #18's history-loop: "has the bot already asked the closing question" is a persistable boolean, not a per-turn N-call classification. #10 attribute availability is a *borderline* case in the other direction — asking an LLM whether structured catalog columns contain a value, when `flavor`/`size`/`color` are literal DB fields (a SQL check covers the structured half; the LLM only adds value for free-text/packaging evidence). Conversely, D1 shows the pipeline *does* know how to build deterministic guards — it just feeds them the wrong input.

## Output integration

How classifier outputs are (or are not) correctly reflected in the customer-visible reply:

- **Order-confirmation formatting (S-50)** — works as designed when #16 fires: delivery-ETA line canonicalized from tenant config + fixed follow-up injected (processAIReply.ts:2578-2590). Integration defect is downstream: the *formatted confirmation* is then scored 0.200 by #22 (every dev confirmation, EV-018), requiring the #17 veto — and the one confirmation that slipped past the veto was flagged and **re-fed as an assistant turn** into the next reply's context (EV-022, DP-pc-14).
- **Partial answers (S-48)** — #11's grounded `answer` + missing[] labels are correctly assembled into a partial answer + "we'll notify you" + alert. Two integration defects: nothing in the system tracks the promised follow-up (Ph-4: 16/20 escalations are conversation-terminal, EV-014), and the escalation turn persists `product_ids = []` (DP-retrieval-12), destroying the anchor the *next* turn needs — escalations manufacture the retrieval failure that causes the next escalation (Trace 2, three anchor-loss events).
- **Discount silence** — #25 true + prior finalized discount → `[NO_REPLY]`: a classifier output integrated as *total silence* with no persisted record on the customer-visible timeline (DP-gg-05, DP-gg-07).
- **Holding-message replacements** (#21, D1, #11, usage family) — integrated by *replacing the entire reply*; on 06-27 the replacement text itself was mojibake (`S� shpejti…`, EV-011 note) — the replacement path lacked the encoding treatment of the main path.
- **Image-request override (S-61)** — #28's output is integrated *after* the sanitizer and only on no-escalation turns; a late override slot that fails open to the original reply.

**Fail-open/closed asymmetry — where a tool failure propagates into a wrong decision:**

| Tool failure | Direction | Customer-visible consequence | Business consequence |
|---|---|---|---|
| #11 gap assessor errors (only fail-closed) | **closed** | Every product question → holding + pause + alert during an OpenAI degradation | Alert flood; conversations terminated (EV-014 pattern) |
| #2/#3/#6 transport error (umbrella, DP-GPR-28) | open | Refund/cancel demand gets a normal sales reply | Compliance/trust; no alert trail |
| #5 affirmation missing confidence (no boost) | closed-silent | "Po" consent ignored → no draft order | Order + 5% commission forfeited, no signal |
| #2/#3/#6/#7 missing confidence (boost, DP-GPR-16) | open-aggressive | Escalation/order-mutation fires at manufactured 0.85–0.9 | False escalations; unaudited order edits |
| #8 empty-completion throw (DP-po-18) | closed-silent | Nothing visible | Order + commission forfeited, green job |
| #22 eval null | open | Unscored reply sent | Quality telemetry gap |
| #21/D1 with empty retrieval set (DP-gg-31/DP-gg-26) | open when retrieval fails, **false-closed when retrieval partially hits** | Correct answers replaced by holding messages (3/3 dev alerts); wrong names unguarded | Escalations on correct replies; guard coverage inversely correlated with need |
| #34 query-embedding race (DP-retrieval-01/23) | open | Keyword-only retrieval → wrong/empty product set | Feeds every row above |

The asymmetry is systemic: **the only guard that blocks (fail-closed) is grounded on the least reliable input, while every guard protecting revenue-critical paths (order consent, intent detection) fails silent-negative.**

## Cost & latency profile

**Call-chain length.** Per inbound text message, serialized LLM completions (census, `02-execution-trace.md` / mapper fan-out): typical happy path **~15–20 calls**, worst case **25+** — language, 2–4 pre-reply detectors, 2 order-signal calls, 4 parallel routing classifiers, conversation-ending, **main reply**, usage gate (+up to 3 usage/gap/health calls), 3–4 reply-shape calls (+N order-closing history calls), quality eval, name guard, intent detection, and the 2 repeated order-signal calls. Only two batches run in parallel: the 4 routing classifiers (aiService.ts:3487-3496) and the image-request classifier (processAIReply.ts:1951-1955). Everything else is `await`-serialized.

**Timeout stacking.** The shared client (openaiClient.ts:15-29) sets `timeout: 60_000`, `maxRetries: 3` — a single degraded call site can consume up to ~4 × 60 s before its verdict resolves. With ~15–20 serialized sites, the theoretical worst chain is far beyond any operational bound; the practically binding constraint is the **300 s conversation lock TTL** (DP-GPR-04): *two* fully-degraded serialized calls exceed the lock, after which a second worker can enter the same conversation mid-pipeline. Exactly **one** classifier has a real per-call budget — #10's 6 s AbortController (productAttributeAvailabilityService.ts:36) — and the query-embedding path's 5 s race is **non-aborting** (DP-retrieval-23): the loser keeps consuming a connection for up to the full SDK budget. There are no per-classifier latency budgets, no circuit breakers, and BullMQ retries re-run the *entire* chain including all prior successful calls (DP-iq-26), with the 25/h rate counter INCRing per attempt (DP-iq-21).

**Cost profile.** Per-message OpenAI spend is dominated by call *count*, not per-call size: classifier outputs are capped small (16–512 max_tokens; most 64–200), but each call re-sends its own input context. The main reply's system prompt alone is evidenced at **~26–33 K chars (~6.5–8.3 K tokens) per text turn** with the 17,907-char guidelines block always on (prompt mapper; the history budget of 6,000 tokens does not cover the system prompt). Classifier inputs range from the inbound text alone to inbound + recent history + product context (#8 injects catalog names; #11 receives the full product knowledge context). No classifier uses the per-tenant fine-tuned model even when one exists — ~28 of 33 text classifiers run on `OPENAI_CHAT_MODEL`; only #8 (INTENT) and #22 (EVAL) honor their dedicated env vars (mapper §Model roles). Precise per-message token totals are not derivable from evidence (no prompt log exists — Ph-4 method note); the defensible statement is: **a single-call-plus-deterministic-guards design would remove 14–24 completions per message**, which is what the Merge/Replace dispositions above sum to.

## Business-logic placement

Where each validation actually lives — prompt (asks the model to behave), tool (LLM classifier), or backend (deterministic code/DB). Observation table; no recommendations beyond the dispositions above:

| Business concern | In the prompt | In an LLM tool | In backend/deterministic code | Observation |
|---|---|---|---|---|
| **Price truth** | Catalog context injected with prices; guidelines instruct price fidelity | — | D1 regex guard post-hoc, vs **per-turn retrieval set** (not DB); D3 cross-turn price consistency | Price truth is *checked* deterministically but against the wrong source; the DB — the actual source of truth — is never consulted at guard time (EV-011/013). |
| **Availability truth** | "No matching products" context string | #19 classifies whether the *reply* claims unavailability | none — no catalog existence check on denial claims | The system verifies the reply's *shape*, not its *truth*: the AI can deny an in-catalog product and no component checks the catalog (Trace 3; DP-retrieval-13/15). |
| **Attribute availability** (flavor/size/color) | product context | #10 LLM over catalog rows | `VALID_ATTRIBUTE_KEYS` intersection; structured columns exist in `products` | Structured DB columns are interrogated via LLM rather than SQL; the LLM earns its place only on free-text/packaging evidence. |
| **Order fields** (name/phone/address) | prompt asks the model to collect them | #8 extracts from conversation; #7 extracts updates | phone additionally resolved deterministically from contact metadata / WhatsApp id (processAIReply.ts:3536-3545); 7-conjunct validation gate | Split-brain: extraction is stochastic, validation is deterministic, and #7's output writes the order directly (DP-GPR-27) while #8's feeds a gate. |
| **Order consent** | prompt asks for explicit confirmation | #5 + #4 (+#8 `is_ready_to_order`) — disjunction | `INTENT_THRESHOLD` comparison | Consent — the commission trigger — is a disjunction of independent stochastic verdicts with inconsistent confidence semantics (DP-po-21, DP-GPR-16). |
| **Delivery ETA** | — | #16 detects a confirmation reply | ETA text canonicalized from `tenants.delivery_time` config (S-50) | The best-placed logic in the pipeline: config-owned truth deterministically injected; only its *trigger* is an LLM. |
| **Escalation policy** (cancel/refund/health) | guidelines blocks describe restraint | #2/#3/#6/#15 detect; thresholds in code | canned responses + pause + alert in code | Policy thresholds (0.8/0.82/0.7) live in code, but whether they're *reached* is decided by boosted model confidence — policy effectively delegated to the classifier's JSON habits. |
| **Duplicate order suppression** | — | — | app-level read-then-insert scan, no DB constraint (DP-po-26/27) | Deterministic but not transactional; DB owns no invariant. |
| **Commission eligibility** | — | — | SQL session-window check, NOW()-relative (DP-po-28), decided at draft creation | Fully backend — correct placement, timing-sensitive evaluation. |
| **Reply language** | `{{TOKEN}}` placeholder map keyed by locale | #1 | heuristic fast-path; `'sq'` default | Three layers for one bit; default direction hardcodes the primary market. |

The placement pattern: **truths the backend owns cleanly (ETA, commission window) are the components with no Phase 3/4 findings; truths delegated to per-turn LLM verdicts over retrieval snapshots (price, availability, product identity) account for every guard false positive in the dev data.**
